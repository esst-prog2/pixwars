# Planning log

One line per decision: the date, what was decided, and who decided it.

- 2026-09-27 — Adopted OpenSpec (`@fission-ai/openspec`, spec-driven schema) as the planning workflow for this project; added `AGENTS.md` with a planning-log rule and a `CLAUDE.md` that is just `@AGENTS.md`. (me)
- 2026-09-27 — MVP boundary: local single process, no sockets. The README's "first useful version" was seven systems at once; the network layer becomes change request #2 instead, as the README's own week-six checkpoint argues. (me)
- 2026-09-27 — MVP players: one human on the keyboard plus one dummy bot opponent, so the full win condition is reachable without a network. (me)
- 2026-09-27 — MVP includes all four core systems: blocks, beds, melee, and the iron generator + shop. Nothing from the core loop deferred. (me)
- 2026-09-27 — Done bar for the MVP: headless pytest over the simulation, plus a window that actually plays. (me)
- 2026-09-27 — Simulation runs at a fixed 20 Hz with rendering at 60 fps, from day one, so the later network port does not change how the game feels. (me)
- 2026-09-27 — Map is all five platforms from the README, hardcoded in the sim; loading maps from files is a later level. (me)
- 2026-09-27 — The bot produces the same button-state struct a keyboard does; no AI inside the simulation. (me)
- 2026-09-27 — Repo is a uv workspace: one pyproject.toml per package plus a root workspace, with `python main.py` as the entry point. Import boundaries enforced by packaging, not convention. (me)
- 2026-09-27 — Client depends on pygame-ce rather than upstream pygame, because Python 3.14.7 is unlikely to have upstream wheels. Same `import pygame` API either way. (me)
- 2026-09-27 — MVP UI is the header (iron count, bed-destroyed state) plus an end-of-match scoreboard — exactly the demo the README narrates. No lobby screens, since there is no network yet. (me)
- 2026-09-27 — Shop is a walk-in zone on your own island with number keys 1-4 to buy; no modal overlay, because a pause-for-one-player overlay breaks once the sim is authoritative. (me)
- 2026-09-27 — Wrote the change request `openspec/changes/pixwars-mvp/` (proposal, 7 capability specs, design, tasks); later levels listed in the proposal only, deliberately unspecified. (agent)
- 2026-09-27 — Split the MVP into seven capabilities (match-simulation, block-building, resource-economy, beds-and-elimination, melee-combat, bot-opponent, game-client) rather than one `gameplay` spec, so later changes can modify one system without resplitting requirements. (agent)
- 2026-09-27 — Positions and velocities are integers in 1/256-of-a-tile subpixels, not floats, because determinism and the half-tile-per-tick collision guarantee become plain integer assertions. (agent)
- 2026-09-27 — Fixed phase order inside a tick: purchases, physics, building, combat, match, generators. Combat before match resolution is what makes "the match ends on that same tick" true. (agent)
- 2026-09-27 — The bot lives in `pixwars_client`, not `pixwars_sim`, and the sim's import boundary is enforced by a test that walks its imports. (agent)
- 2026-09-27 — Amended the map requirement in `specs/match-simulation`: instead of "no gap can be jumped", the invariant is that the route *toward the enemy base* is impassable unaided, while dropping back onto your own base is allowed. Reason: a downhill hop is always jumpable given a jump height tall enough to climb one placed block, so the original wording would have forced a map roughly 90 tiles wide for no gameplay gain. (agent)
- 2026-09-27 — Map geometry: bases at rows 27 (x1-11, x52-62), middles at row 22, center island at row 16. Every forward gap is blocked by height (5 rows up, against a jump of 2.9 tiles) rather than by width. (agent)
- 2026-09-27 — `place_target` prefers the floor under the player's own leading edge before the tile beyond it. Found while writing the bot: a player straddling two columns would otherwise bridge one tile too far and walk into the hole they left. (agent)
- 2026-09-27 — The bot breaks beds only, never placed blocks. It was demolishing its own bridge one tick after laying it. (agent)
- 2026-09-27 — The bot decides "have I finished shopping?" by scanning the map for a block its own team has placed, since it keeps no state of its own and placing blocks otherwise drops its stack back below the shopping threshold forever. (agent)
- 2026-09-27 — Players are grounded at a spawn point rather than falling one tick first, so a jump on the tick you spawn is not swallowed. (agent)
- 2026-09-27 — The frame/tick accumulator counts integer nanoseconds, not float seconds: 1/20 s is not binary-exact and `0.5 // 0.05` is 9, which silently dropped a tick every half second. (agent)
- 2026-09-27 — Shared test helpers live in `sim_helpers.py` and `client_helpers.py` rather than in the two `conftest.py` files, which collide on the module name when both suites are collected together. (agent)
- 2026-09-27 — MVP verified: 111 tests pass headlessly, and the real window runs at 60 fps over a 20 Hz match. (agent)
- 2026-09-27 — Synced the seven delta specs into `openspec/specs/` without archiving, so the repository holds both the spec and the change request it came from. The change stays active; archiving is a later step. (agent)
- 2026-10-02 — Network spike lives in `spike/net/` (`host.py`, `echo.py`), outside the three packages, since it is a throwaway measurement and not the server. (agent)
- 2026-10-02 — The spike loads `bot.py` by file path rather than importing `pixwars_client`, whose `__init__` pulls in pygame. (agent)
- 2026-10-02 — Round-trip time is measured on the host's clock only, so the two machines need no clock sync; the echo side logs arrivals so downstream loss can be told apart from upstream. (agent)
- 2026-10-02 — Only I commit and push. The agent leaves its work in the working tree on `hw4-spike` and stops there. (me)
- 2026-10-02 — Spike question, taken from issue #3: at 20 Hz on the room's wifi, what is the round-trip latency and loss for one real PixWars snapshot, raw pickle against zlib-compressed? An answer is four numbers — p50 and p99 round trip in milliseconds and loss as a percentage, at both sizes — from 60 s per size between two machines. Under roughly 50 ms and 1% the network port is safe and gets built; above that, the README's week-six checkpoint has fired in week five. (me)
- 2026-10-02 — The spike is not put through an OpenSpec change: it adds no behaviour to the game and touches nothing under `packages/`. Whatever the answer changes (snapshot format, the README's risk section) does go through one. (agent)
- 2026-10-02 — Added `spike/net/report.py`, and `host.py` prints through it, so the logged numbers come from one function that anyone can re-run over the committed CSVs without the wifi or a second machine. (agent)
- 2026-10-02 — Loopback runs are for checking the scripts only and are never written to `spike/net/out/`; that directory holds the two-machine wifi measurement and nothing else. (agent)
- 2026-10-02 — I have one laptop, so machine B of the spike is my Android phone running `echo.py` in Termux, on my home wifi rather than the classroom's. The result is labelled that way. (me)
- 2026-10-02 — `echo.py` runs as a single file with no checkout: when `pixwars_sim` is not importable it replies with the same pickled `Buttons` bytes, embedded verbatim. A phone then needs one file and stock Python. (agent)
- 2026-10-02 — Spike measured, home wifi, laptop to Android phone, 1,200 snapshots per size at 20 Hz: raw (5,363-5,376 bytes, four fragments) p50 10.9 ms, p99 61.2 ms, loss 0.00%; zlib (613-647 bytes, one datagram) p50 9.8 ms, p99 81.4 ms, loss 0.00%. Median and loss are under the issue's bar of roughly 50 ms and 1%; p99 is over it at both sizes. Evidence: the four CSVs in `spike/net/out/`, reproduced by `python spike/net/report.py`. (agent)
- 2026-10-02 — `report.py` counts only sequence numbers the host sent when reading the echo log: six 29-byte datagrams from some other device reached the phone's open port during the raw run. The CSV is kept as received. (agent)
- 2026-10-02 — Spike answer: the network port is safe to build. p50 is 10.9 ms raw and 9.8 ms compressed against a 50 ms tick, and loss is 0.00% over 2,400 snapshots. p99 is 61.2 ms raw and 81.4 ms compressed, over the roughly-50 ms bar, and that is treated as a design constraint rather than a stop: about 1 round trip in 20 misses its tick, which a client that keeps drawing the last snapshot shows as a stutter. I asked the agent to judge the numbers, so the judgement is its own. (agent)
- 2026-10-02 — What the answer changes: README section 5 now states the measurement and two constraints for the network change request — the client never blocks waiting for a snapshot, and snapshots are sent zlib-compressed as one datagram. Compression did not improve latency in the measurement; it is chosen so a lost fragment cannot cost a whole snapshot. No network code or spec is written in this spike. (agent)
